How AI builds and runs Poesys

Poesys is a simulated GB energy supplier, living through the real 2016–2025 market, and it is built and operated by AI agents with one human setting direction. This page shows the system of checks between an agent's idea and a published claim, how much it has built, and what it learned from what broke. What the supplier itself can do is on Capabilities.

In brief

  • One human, many agents. A director sets the purpose. AI agents write the direction, the code, the tests and this site, and run the simulation, continuously.
  • Eight layers of checks. Every change passes through them on its way from an idea to the published page. The stack below names the code file that enforces each one.
  • Checks are proven able to fail. A check counts only once it has been seen catching its own defect, put back on purpose. A check that cannot fail is treated as worse than none.
  • A measurement a real supplier cannot make. Because the world is simulated, the gap between what the supplier believes about its customers and what is true can be measured. It is shown below.
  • The mistakes are published. Each became a rule that now runs as code.

Everything an agent proposes passes down this stack before a reader sees it. Where belief and truth diverge

The company inside the simulation cannot see the world it lives in — it infers. This is the measured size of the gap between what it believes and what is actually true, which is the only number on the site that could not exist outside a simulation.

How the gap is measured

The gap is measured, not asserted, and the measurement is deliberately made against something the company has no way to reach. Its picture of the world is assembled only from what a real supplier could observe: prices it was quoted, meter readings it received, bills it issued, payments that arrived or did not. Ground truth sits on the other side of a wall the company has no call into, and the two are compared afterwards, here, by the harness.

Where they diverge, the company is left wrong on purpose. A supplier that discovers its own error the instant it makes one is not a supplier — it is a lookup table with a story attached. The interesting question is not whether the company is right; it is how long it takes to notice it was wrong, and what that costs in the meantime.

Lessons it learned the hard way

Each one cost something, and each left a rule behind that now runs as code. The full story of each sits in the sections below.

20 August 2026

The site that looked broken and was not

What happened. The site appeared to fail up to 47% of page loads. Four explanations were tested and each was wrong. The host's analytics were counting one kind of request twice, and the site had been healthy throughout.

The rule it left. When explanations keep dying, check the instrument before proposing another. And a check through a cache can confirm something is there but never that it is gone, so every live check now asks the source.

4 September 2026

Green tests, stale code

What happened. Ten of eleven background processes were running code up to eleven days old, while every health check called them healthy. A passing test proves the code is right, not that it is the code running.

The rule it left. Each process is graded on whether any module it loaded has changed since it started, and is restarted when one has.

August 2026

Five checks, all pointed slightly off-target

What happened. In one day, five checks that existed, were wired in and looked right were found catching nothing. One reported its own failure and then exited as a success, so months of deploys were recorded green.

The rule it left. A check counts only once it has been seen failing on its own defect. Checks are counted by that, not by whether they exist.

Meaning, learning, and what it is not allowed to do

Four ideas that set this system apart, with their live counts

In brief

  • One word, one meaning, checked where parts meet. Tests go red when two parts of the code disagree about what a word means.
  • Experience becomes knowledge, and knowledge becomes a check. A mistake is written down, grouped with others like it, and turned into a rule that runs.
  • It may not tune itself to a score. Its outputs are diagnostics, never targets.
  • Its reviewers are graded too, on whether the work they passed later proved wrong.
  • Concepts checked where parts meet: 18 claims on the canon page checked against the code; 21 named checks that refuse an impossible state in the supplier's records; 6 figures from the Knowledge pages tested against the simulated world.
  • Experience to knowledge to a check: 452 findings filed to the work queue in the last 30 days; 6 class documents that consolidate the recurring ones; 8 ratchet tests, which freeze an old backlog and fail only when it grows.
  • Judging the judges: 11 sign-offs by fresh reviewers have been followed up, including a blind trial on commits known to be bad; 4 of them let through a defect found afterwards. A sample this small measures the reviewers roughly, and is shown because it is the real count.

Meaning. Many teams draw their concepts as a box of definitions. Here a concept is exercised rather than listed: one simulated household is walked from its meter readings to its bills with every join between the parts asserted; the supplier's records are checked against states that cannot happen; the claims on the project's own canon page are checked against the code; and the published figures on the Knowledge pages are tested against the simulated world every week. The reason is a real one. One legal requirement, how VAT applies to a household bill, was found implemented five times; a defect fixed in one copy in July was still live in another in August, and nothing could notice. A test that reads the meaning at the joins can.

Learning. Individual findings are filed as they are made. Recurring ones are consolidated into class documents, and a class produces a rule or a ratchet: a test that freezes an old backlog at today's size and fails only if it grows. A check that keeps refusing becomes a piece of work, not something to retry. The lessons above are this flow's record.

What it is not allowed to do to itself. Some recent agent systems, GEPA among them, rewrite their own prompts to raise a score. Poesys refuses that by design. What it measures is there to show where it is wrong, never to be optimised, and a check pinned to today's answer is itself treated as a defect, because it goes red when the code becomes more honest. The rule is held by tests/company/test_carbon_not_a_target.py, which fails if a decision can reach an output it is only meant to report.

Judging the judges. An AI reviewer's opinion cannot be tested by putting a defect back, so it is tested by outcome: each sign-off is followed up, and a defect found later is charged to the review that passed it. In a blind trial on 17 October, reviewers given old commits we know were bad named the defect in one of five, and pointed at it in three.

What we are building next
  • Asking any question of a past run. Each run is recorded in a ledger, but there is no wide per-run record yet, so a new question about an old run needs new code.
  • A reviewer that reads every change. The 17 October trial measured it: it catches some defects, and most of its other findings on clean commits were real. The proposal is to run it, not blocking, on two narrow triggers.
  • Landing in batches, then bisecting a failure. Whether it would cut the time spent in the gate is an open question, staged on 15 October.
  • A regular audit of what has been switched off. It has no trigger or schedule yet.

Two-way doors, pace and how work is balanced

How it decides, how it spends, and how it divides its time

In brief

  • Act by default. Almost every decision can be undone, so it is taken and logged. A short list, in code, is reserved to a human.
  • Spend where depth compounds. Only three routes can start an AI session, and the top model is the default.
  • A map, not a plan. Work is drawn from small pieces, each with the evidence it needs; dials order the work but never stop a part of it.
  • Two-way doors: 7 kinds of action are reserved to a human; 12 questions raised to the director in the last 30 days, 11 still open, none of which stops other work. How many actions proceeded without asking is not recorded, so it is not measured yet.
  • Effort and pace: 3 unattended routes can start an AI session, and nothing else spends; 1,071 sessions started in the last 30 days, 98% on the top model.
  • How work is balanced: share of commits that changed the world or the supplier, by week: 31 Aug 6%, 7 Sep 7%, 14 Sep 4%, 21 Sep 4%, 28 Sep 14%, 5 Oct 24%, 12 Oct 15%, 19 Oct 18%. Every other commit changed the machine that builds them.

Two-way doors. The burden of proof sits on "this cannot be undone". When an agent is unsure, it proceeds and records how to reverse what it did, and a needless escalation counts as a defect, just as a needless stop does. A wrong reversible decision costs about an hour of computing; a stall costs the director's attention, the one scarce resource. The list that does stop it is held in background/one_way_door.py: real money, real people, real-world commitments, public claims that cannot be retracted, live credentials and the safety controls, and destroying evidence. Over all of it sit a director-only kill switch and a dead-man's switch that watches for real commits.

Effort and pace. What spends was measured before anything was designed to limit it: only three unattended routes start a model session (background/tick_mode.py), so nothing else needs throttling. The model is matched to the work, not to the process (background/model_tier.py): the top model is the default and the fallback, and a cheaper one is reachable only for named kinds of routine work. In the director's words: "I'd rather spend the tokens than get shallower work." He supplies a reading of the weekly allowance, and the machine paces itself against it with one dial that returns to normal when its time is up.

How work is balanced. Work is drawn from a map of small pieces, not taken from a schedule; when a date and a test disagree, the date is wrong. The planning agent can make a piece of work more likely but never impossible, so a wrong instruction slows the machine and never wedges it. And when something that just landed is contradicted downstream, that comes first, ahead of anything new.

How the work is chosen

In plain English, because the machinery is the subject here.

How the queue is ordered, in four paragraphs

There are two seats. A director decides what matters and rules on anything irreversible; he does not write code. A builder — this system — designs, builds, checks and ships everything else, on its own, continuously.

Work is held as a map of small pieces, each with a claimed level of maturity and the evidence that would have to exist for that claim to hold. The builder draws from the map rather than from a plan, so the order of work follows what is now provable rather than what was scheduled months ago. A piece cannot claim a higher level without leaving a record of why; a claim with no record is refused at the point of commit, not at review.

The rule that does the most work is the dullest one: a check that cannot fail is worse than no check at all. Every control has to be shown firing on the exact defect it claims to catch, by deliberately reintroducing that defect. Most of the entries in the record below were found that way — a control that looked right, passed, and was measuring nothing.

What actually orders the queue is not a plan. Plans exist and are kept, but a date in one has never been allowed to shorten a check or promote a piece of work: when a date and a test disagree, the date is the thing that is wrong. What wins instead is whichever piece of work most shortens the distance between doing something and finding out whether it was right — because that distance, compounded, is the whole difference between a system that improves and one that merely accumulates.

Checks that can actually fail

Every control in the system, graded on whether it has been proven to fire on its own named defect. The ones that have not are counted rather than quietly trusted.

The three ways a check passes while meaning nothing

There are three ways a check passes while meaning nothing, and this project has shipped all three. It can derive the value it is checking from the same place it checks against, so it can only ever agree with itself. It can pass when its input is missing, empty or malformed. Or it can pass when the checker itself could not run — which is the worst of the three, because an unavailable check and a satisfied one look identical from outside.

A live example, removed the same day this was written: the step that cleared this site's cache after every deploy had been misconfigured since the day it was added. It reported its own failure and then exited successfully, so every deploy for months was recorded green while the step did nothing at all. It has been replaced by a check that fetches what was just published and compares it, byte for byte, against what a reader is actually served.

The rule that shapes this list

One rule shapes this list more than any other, and it was learned the hard way. A check that observes new content is trustworthy; a check that concludes something is absent is not. A cached copy of a page can be old, but it can never be newer than when it was stored — so through a cache, "this is gone" and "I am looking at a stale copy" are the same observation. On 20 August, eight deleted pages went on being served to readers for a day after every published check had confirmed them removed. Every live check this project makes now carries a one-off marker that a cache cannot answer, so the question can only be settled by asking the source.

The rules this project has had to mint

Each of these exists because something broke. They are shown newest first, each in the words the canon gives it now, with the failure that caused it, because the failure is the useful half. Where a rule has been reworded since it was learned, the original wording sits under it.

Why a rule counts only when it runs

A rule earns its place here only by being converted into something that runs. Written rules decay — this project has watched several of them do it, always the same way: the rule stays in the document, everyone agrees with it, and the behaviour drifts back because nothing was checking. So the test applied to every rule below is whether you could delete the sentence and still have the rule hold. If not, it isn't a rule yet.

The most useful thing this list has taught is about the shape of failures, rather than any single entry. Almost nothing here was caused by a missing check. In one day of August 2026 five separate controls were found to be present, correct in intent, wired in, and pointed slightly off-target: a cache-clearing step that reported its own failure and then exited successfully, so months of deployments were recorded green; a rule requiring a change to be recorded alongside the code, enforced only by a check that never ran on that code; a guard that reported "I could not ask" as "the answer is empty"; a batch of timeouts that turned out to be an artefact of the measuring instrument rather than the thing measured; and a stall detector whose notion of progress was satisfied by other people's work.

Every one of those reads as green until something forces a second look. That is why the section below counts controls by whether they have been proven to fail rather than by whether they exist, and why the entries here name the failure and not just the remedy — a rule remembered without its failure is the first step back to not having it.

What we know is wrong

Standing weaknesses, stated here rather than discovered by a reader.

The 20 August episode in full

Two kinds of wrong live in a project like this, and they are not equally interesting. The first is something that does not work yet — a gap, listed below, with no pretence that it is finished. The second is something that works and is believed for the wrong reason. That is the kind that does damage, because nobody goes looking for it.

The second kind is only ever caught by a measurement that could have come out the other way. On 20 August this site appeared to be failing between eleven and forty-seven per cent of its page loads. Four explanations were proposed, and each one was tested, and each one was wrong: a caching header, a stale purge, a theory that the failures were only this machine's own checks, and a routing pattern that held across eight hundred observations and broke at fourteen hundred. None of it was real — the hosting provider's analytics were recording every request of one protocol twice, and the second copy read as a timeout. The site had been healthy throughout.

Two things were worth more than the answer. An observed pattern is still only a theory about the next observation, however many observations it already survived. And when four explanations about a mechanism die in a row, the next move is not a fifth one — it is to check whether the instrument means what you think it means. The four wrong turns are kept in the record deliberately: a project that publishes only the theories that turned out right is showing you its results, not its method.

How the three kinds of agent divide the work

Three things run here. A tick wakes on a timer, takes one piece of work, does it and exits. A builder's seat works when a human hands it a turn. Neither of those decides what matters — so a third, the delivery seat, wakes every few hours, reads the stretch just gone, and writes down what the next one should be. It writes direction and never code. What it decides makes some work more likely to be picked up next; it can never stop any work being picked up at all, which is deliberate — a wrong instruction should slow this machine down, never wedge it.

The most a carbon score could ever be worth

Same discipline, different programme: before building a thing that tells a household when to use electricity, measure the most that could ever be worth if it worked perfectly. Perfect foreknowledge of the grid's hour-by-hour carbon, perfect compliance, every kilowatt-hour moved. That is a true ceiling — no buildable method beats it.

What code each daemon is actually running

A green test proves the code is right. It proves nothing whatever about the code being loaded: a long-lived process holds whatever it imported when it started, and on 2026-09-04 ten of eleven daemons here were running code up to eleven days behind the repository — one of them holding 146 changed modules — while every liveness surface called them healthy. Two ages are shown because they answer different questions. Running age is how long the process has been up, and long is not wrong. Loaded-code age is how old the code it holds is. A daemon restarted an hour ago onto a stale checkout has a small running age and a large loaded-code age, and only the pair can tell you so. The verdict is neither: it is whether any module the daemon imports has changed since it booted, so a daemon days behind in time that holds nothing which moved is current, and reads as current.

What this page is not. It is not a dashboard, and there is no view behind it showing atom identifiers, internal level numbers or ledger records. Those exist, and they are how the system checks itself, but they are written for the machine and reading them tells you less than the numbers above.

A stretch is the few hours between two of the delivery seat's readings, described below.
