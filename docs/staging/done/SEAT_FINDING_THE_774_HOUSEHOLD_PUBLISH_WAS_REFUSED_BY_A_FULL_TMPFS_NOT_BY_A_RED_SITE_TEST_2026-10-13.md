# The 774-household publish was refused because /tmp filled up, not because a site test was red

**Fate (2026-10-14):** DONE -- 0d5304e98 fixed the ENOSPC cause and the publish went out as ed3dadd9d.

*Delivery seat, 2026-10-13 ~21:00Z. Drawn as `the-publish-run-of-2026-10-13-reaches-origin`.*

**What happened to the runs.** The 11:24Z run (pid 2607003, stamped 2248e3baf) did not die on a `None`. The
runner killed it at its fixed 7200 s timeout (`Run TIMED OUT after 7200s`, journal 13:24Z). That timeout has
since been replaced (`background/sim_runner.py`, `LEGACY_RUN_TIMEOUT_S`). The 13:44Z retry, with the same stamp,
finished in 6929 s. Its publisher (`process_run_complete`, from 19:57Z) passed the `tests/` gate in 1050 s.
At 20:50Z the site-lane gate refused the commit with **72 failed, 7 errors** (outcome `commit_refused`, rc 77).
No figures reached origin.

**The cause, with a one-variable control.** The same six site files the journal named, run against the
shared tree's regenerated bytes:

| TMPDIR | Result | /tmp free before → after |
|---|---|---|
| `/var/tmp` (disk) | 82 passed | n/a |
| default (`/tmp`, a 12 GB tmpfs) | 76 passed, 6 errors | 2.6 GB → 488 KB |

`site/test_ia_register.py`'s `tree` fixture copied the whole `site/` directory into `tmp_path` for each of 18
tests. The 774-household regeneration grew the shared tree's `site/` from 58 MB to 180 MB (`data/` 107 MB,
`state/` 66 MB). That is about 3.1 GB per run, and pytest keeps three basetemps. /tmp is RAM-backed and shared with
every lane, so once it filled, every test in the site lane that touched a temp file failed with it. The site
lane reported those failures as red tests. (0d5304e98 confirms the errors are `[Errno 28]`.) This turn's own tool output was also lost to ENOSPC at about 20:58Z.

The order fits too. `test_ia_register.py` sorts before every `site/test_the_*` file, and every FAILED file the
journal's tail names is a `test_the_*` file that runs after it. In my control, the four files that ran
*before* `test_ia_register.py` passed, and only the one after it errored. The 72 failures are what you would
expect from a cascade once /tmp had filled. I have not re-run all 79 one by one.

**So the bigger book is what broke the publish.** Nothing in the site's code was wrong. The 2.8x larger book
(see 85e411af4) grew the feeds, and a fixture that scales with the feeds ran out of a shared, fixed tmpfs.

**Fixed, by two lanes at once.** A worker tick reached the same diagnosis and landed the fixture fix first,
as 0d5304e98 (it skips `*.json` and `*.jsonl`). It read the tracebacks directly: `[Errno 28] No space left on
device` under /tmp/pytest-of-rich. That confirms the cause this finding could only infer. This seat's
parallel fix was dropped in favour of theirs. What lands from here is the control that the slimmer copy does
not leave out an input: `test_the_copy_carries_every_input_the_register_reads` asserts that the copy carries
every page, `sitemap.xml` and `_redirects`, and classifies and routes exactly like the real site. Mutation: also
ignoring `sitemap.xml` reds it.

**Not fixed, open.** No gate checks free space on /tmp before a long suite runs, so a full tmpfs is still read as a
red test. The other `pytest-of-rich/pytest-N` directories, and any lane's large tmp files, can still fill it.
The site lane could set `TMPDIR` and `--basetemp` to disk. That is one line in `tools/site_lane_gate.py`, but it
changes a gate every lane runs, so I have left it to its own item.

**The `startup-anchors REFUSED` lines** in the same stderr (LATEST.md and PROJECT_STATE.txt "really changed
2026-10-05") come from the publisher's report-only pass, which runs before it stages anything. The `--gate` pass
at commit time dates a staged anchor as today, so those lines did not block this publish.
