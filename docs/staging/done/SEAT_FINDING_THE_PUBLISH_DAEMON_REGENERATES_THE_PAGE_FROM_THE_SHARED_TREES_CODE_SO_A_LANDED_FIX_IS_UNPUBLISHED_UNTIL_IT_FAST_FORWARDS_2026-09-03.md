## What is wrong

`9117878c2` landed and promoted to `origin/main` at 21:51:26+01:00. It stops the value-arms page
stating `resolved: true` on a verdict a third of its own floor's re-draws reverse.

The shared tree `/home/rich/synthetic-enterprise` is at `7304bbe51` (21:33:43+01:00) — **behind** —
and its working copy of `site/data/value_arms.json` carries:

```
resolved                        : True
bound_available                 : True
verdict_withheld_because present: False
generated_at                    : 2026-09-03T20:44:03Z
```

That file was regenerated **at 20:44:03, from the pre-fix code**, and it is uncommitted in a tree
holding 463 modified files. `site/test_the_baseline_comparison_reaches_the_reader.py` is dirty there
too, with another lane's +17/−2, and `grep -c verdict_withheld_because` on it returns **0**.

So two separate things are true at once, and only the first is visible from the lane that landed:

1. The fix is on `origin/main`.
2. The artefact a reader is served is regenerated by a daemon running the **shared tree's** code,
   which does not have the fix, and that daemon has already written `resolved: true` once since the
   repair existed in another worktree.

## Why this is not "just staleness"

Nothing auto-fast-forwards the shared tree. `PUSHED IS NOT IMPORTED` is a known shape here, but the
recorded version of it is about a daemon *reading stale code*. This is one step worse: the daemon
does not merely fail to publish the fix, it **regenerates the defective artefact over it** on its own
schedule. A landed correctness fix and a live process re-asserting the thing it fixed are coexisting,
and the only evidence of the conflict is in a tree the landing lane is structurally isolated from.

The revert is also armed in the ordinary way: a lane committing those two paths from the shared tree
commits a working copy based on `7304bbe51`, which does not contain the re-keyed door rung. The door
suite would then be green against a payload that states a verdict the page's own bound reverses —
the control and the defect restored together, so nothing goes red.

## What makes it invisible

The landing lane's own evidence all passes. `surgical_land` gated the tree the commit would create;
`promote_worktree_landing` reported `promoted 9117878c2 -> origin/main`; `delivery_lane --landed`
bound six paths. Every one of those is true and none of them looks at what is actually being served.
**The seat's completion signal and the reader's experience are measured in different trees**, and the
gap between them is exactly the interval before someone fast-forwards.

`generate_value_arms_data` is invoked from `background/process_run_complete.py`,
`tools/run_value_cycle_ab.py` and `tools/inference_claim.py` — none of which check that the tree they
run in is at `origin/main` before writing a published artefact.

## What I did NOT do about it

I did not fast-forward the shared tree. It holds 463 uncommitted files belonging to other writers,
and my isolation from it is the reason this lane is allowed to run at all. A pure `--ff-only` is the
sanctioned cure for `behind_origin` and creates no tree, but I am not judging another lane's
in-flight state from here, and the two paths at issue are both dirty there.

**This is the disposition, not a request:** the next writer on the shared tree fast-forwards it
before regenerating, and the two dirty paths above are reconciled against `9117878c2` rather than
committed over it.

## The repair worth building

A refusal in the publishing path, not another register: `generate_value_arms_data.generate()` should
decline to overwrite a published artefact when the tree it runs in is behind `origin/main` on **its
own source file**, and say so at the `--out` path rather than exiting quietly. The precedent is this
module's own `PUBLISHING_TREE_COMMIT` block, which already records that the producing and publishing
commits can differ — it *reports* the split and does not *refuse* on it, which is why a daemon could
write `resolved: true` from stale code while the fix sat on `origin/main`.

Note the failure mode to avoid: a refusal that writes nothing is indistinguishable from an OOM kill,
and a refusal must not overwrite a real run. That is a recorded shape in this repository already.

**Not discharged.** No control is claimed for this; it is filed as found. The dirty-path hazard above
is a live condition at the time of writing and will read as historical once someone fast-forwards —
re-establish it before acting on it rather than trusting this paragraph.
