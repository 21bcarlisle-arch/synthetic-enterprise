# `site/data/customers.json` publishes 251 households from a run output containing 19

**Found:** 2026-08-31, while writing a control over the two published rate fields. The control could
not decide what to assert against the live artefact, and the reason it could not is the finding.

## Measured, on `origin/main` at `b8e6ba32d`

| artefact, same commit | content |
|---|---|
| `site/data/customers.json` | **251 legs**, `generated: 2026-08-31T13:22:44Z` |
| `docs/reports/run_output_latest.json` | **19 accounts, 1,600 bills** |

`tools/generate_customers_json` derives the first from the second. Regenerating it in a clean
checkout of that commit produces **19 legs**. So the published surface cannot have come from the run
output committed beside it: **it is a figure on a superseded clock**, and the two have been drifting
apart with nothing able to notice.

## Why it matters more than a stale number

**A reader of the tree cannot reproduce the published page from the tree.** That is the property the
whole provenance apparatus exists to guarantee — `publish_provenance.json`, the banner adoption
control, the basis gate. Each of those checks that a figure carries a clock; none checks that the
figure's INPUT is the input in the same commit.

It also silently defeats any control written over the published artefact. Mine would have gone red
or green according to when the publisher last ran rather than according to whether the code was
right, so it now asserts on the generator against the run output beside it and says why. That is a
workaround, not a fix: the next author will hit the same wall.

## Which of the two is wrong is NOT decided here

Two readings, and I cannot separate them from the tree alone:

* the **run output** is the reduced one — a scale probe or a partial commit landed over the real
  artefact — and the 251-leg surface is the honest one, published from a full run whose artefact was
  never committed; or
* the **surface** is stale — carried forward from an older full run while the tree moved to a
  smaller book.

The first is more likely given the timestamps, and it is the worse one: it means the published page
rests on an input that exists nowhere, so nothing downstream can be checked against it at all.

## What is owed

**A control that the published surface is reproducible from the artefacts in its own commit** — for
`customers.json` first, then for every `site/data/*.json` with a generator. Cheap to state: run the
generator into a temp file and compare the population it produces against the one published. Not
byte-equality (timestamps move), but the counts must match.

I did not write it here because it belongs beside the publish path rather than beside a rate
control, and because it will be red on landing — which is a decision about the publish gate's
blocking set, not one to take inside an unrelated commit.

**And this commit deliberately does NOT land a regenerated `customers.json`.** Doing so would have
shrunk the published book from 251 households to 19 as a side effect of a rate rename. The generator
change lands; the surface is regenerated by the next real publish, from whatever the real run output
turns out to be.

# RESOLVED, same day — and the cause is a published claim, not a stale count

The document above named the mismatch and asked which of the two artefacts was wrong. Both
questions are answered below, and a SECOND finding was NOT filed for them: two documents about one
defect is what the consolidation gate caught me doing earlier the same day.
# The page said "verified, showing run X" for a month, and X is in no commit

**Found:** 2026-08-31, chasing why `site/data/customers.json` publishes 251 households from a tree
whose run output holds 19. The count mismatch was the symptom. This is the cause, and it is a
published claim rather than an internal one.

## What is on the public endpoint

```
site/data/publish_provenance.json
  verification_state : "verified"
  showing_run.run_id : "run_output_5ccc0e0c8_20260831T130500Z.json"
  showing_run.git_commit : "5ccc0e0c8"
```

**That run file is in no commit.** The tree tracks seven `run_output_*` artefacts; the newest dated
one is **18 June**. The newest publish commit that carried a run output is **2026-07-29** — thirty-
three days before the stamp above claims to have verified against one.

So a reader is told the figures were verified against a named run, and there is nowhere to go and
look. The `git_commit` beside it *does* exist and *is* checked — which is the shape of the hole.

## The two populations, and why the fossil is not the answer

| artefact, same commit | accounts | bills | revenue | shape |
|---|---|---|---|---|
| `docs/reports/run_output_latest.json` (tracked) | **19** | 1,600 | £14.06M | 12 resi, 2 SME, **5 I&C** |
| the live run (uncommitted, 27 MB) | **251** | 10,948 | £801k | 249 resi, 2 SME |
| `site/data/customers.json` (published) | **251** | — | — | derived from the live one |

The tracked artefact is a **fossil of a superseded era** — an I&C-weighted book from before the
project moved to households. Regenerating `customers.json` from it yields 19 legs. Verified by
regenerating from the live artefact instead: **same 164 customer groups, identical group set**, 155
of 164 matching on kWh. The published page is derived from the live run and always was.

**So "show 19 and say why it moved" would have been the wrong repair.** 19 is not an older truth,
it is a different world. The page is right; the tree is what cannot back it up.

## Why the surfaces drift ahead of the inputs, structurally

Derived site data is small, so it rides into commits as incidental churn from whichever lane is
committing. The run artefact is **27 MB**, so no pathspec sweeps it and no publish commit has
carried one since July. Nothing anywhere compares the two. The drift is not a lapse; it is what this
arrangement produces by default.

**Retaining the run is not available.** One 27 MB artefact per publish is a gigabyte of machine
output in git within a month. No amount of discipline changes that arithmetic, which is exactly why
the existing guard checked the run's *name* and the *commit* and never the run.

## Fixed: the claim carries what makes it checkable

`showing_run` now carries two more things, and `publishable_violations` refuses a verified stamp
without them:

* **`population`** — `{accounts, bills, total_revenue_gbp}`, a few dozen bytes. The page can now be
  checked against itself: `customers.json` must publish the account count the stamp says the run
  had. Falsifiable without the artefact.
* **`run_retained`** — stated, never assumed. A reader told only "showing run X" will assume X is
  somewhere they could look.

The banner says both: *"Verified … showing run X over 251 accounts and 10,948 bills (the run itself
is not retained in the repository)."* That is strictly weaker than reproducing the run and strictly
stronger than citing a file nobody can open, and the difference between those two is the whole
change.

`tests/background/test_the_page_can_be_checked_against_the_run_it_names.py` holds it — seven legs,
four mutations proven, including the one that stops this becoming an always-refuse: **a stamp naming
an unretained run is publishable.** That is the honest state of this project and refusing it would
wedge publishing for ever. What is refused is publishing it *silently*.

## What is owed, and deliberately not done here

**The live provenance record predates the change**, so the reconciliation leg SKIPS and says so. The
window closes on the next publish and cannot reopen, because `record_verified` can no longer write a
stamp without a population. I did not hand-write a population into the live record: I would have had
to guess which run it came from, and guessing the number that makes a control go green is how a
control stops meaning anything.

**The other twelve generated `site/data/*.json` files carry no population claim at all.** This
change makes one surface checkable. The general property — every published figure reconciles to the
run it is attributed to — is worth having and is a bigger piece than this finding.
