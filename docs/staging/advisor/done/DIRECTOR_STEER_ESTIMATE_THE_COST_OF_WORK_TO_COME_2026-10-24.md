**What was built.**
- **(2) The pace section.** `tools/harness_page_figures.py` adds a "Cost of work to come" row to the Doors, pace and balance block, in plain words: the week's remaining points, what in the priority order fits, the backlog in weeks, and which items to split. The row is dated, and it is marked stale after 7 days. `tools/generate_dashboard_data.py` re-fits the forecast just before it writes the page, so every publish carries a fresh one. `site/harness/index.html` is not regenerated by hand here, because another lane holds it. The next publish renders the row.
- **(3) Estimate and actual.** `background/delivery_lane.draw` writes each Lane 0 item's estimate when it is handed out, and `record_landing` writes the landing. Both go to `docs/observability/.delivery_lane_claims.costs.jsonl` (gitignored, next to the draw ledger). The actual cost is every session that ran `delivery_lane --landed <id>`, subagents included. `tools.work_cost_estimate.render` reports the error by class, and it is the text the Monday and Friday steps of `background/weekly_rhythm.py` print. An item that misses by more than 3x either way is named as BADLY WRONG. Class costs are re-fitted every time the script runs.
- **(4) The flag.** The doorbell opens with `COST FLAG` on any item estimated above 10 points, so the drawer sees it before starting. The draw reads the fit the last forecast wrote, so it never re-reads a month of transcripts.

**Controls.** Tests are in `tests/tools/test_work_cost_estimate.py`, `tests/tools/test_harness_page_figures.py` and `tests/background/test_delivery_lane.py`. Two mutants were run, and both go red:
- dropping the landing record;
