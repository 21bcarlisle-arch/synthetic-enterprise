# Pre-registration: can the shared tree's ahead leg be closed from an isolated linked worktree, and does the merged tree survive the gate?

Written 2026-09-24 ~19:30, BEFORE running the gate. Claim id:
`close-the-fork-the-publisher-has-been-dark-for-68-hours`.

## The state at writing, measured not assumed

- This worktree (`/var/tmp/se-seat-executor`) is at **origin/main exactly**: 0 ahead, 0 behind.
  `checkout_drift()` run here returns `contains_origin: True` — and that verdict is about THIS
  worktree, not the subject. The item's own DONE condition is therefore **already satisfiable by
  the wrong tree**, which is the first thing to record.
- The shared tree `/home/rich/synthetic-enterprise` is **4 ahead, 33 behind** (`fork_state()`
  returns `(33, 4)`). The item was drawn saying 3 ahead; a fourth landed under it.
- Merge base of `origin/main` and the shared HEAD `63356067f` is **`ffa14f065`** — the very commit
  this item was already credited with landing. The credited landing is what the two legs diverged
  from; it did not close the fork.

## The structural fact this turn turns on

`.git` here is `gitdir: /home/rich/synthetic-enterprise/.git/worktrees/se-seat-executor` — a
**linked worktree sharing one object store**. All four of the shared tree's unlanded commits
(`63356067f`, `61b67fa0d`, `13203ed91`, `ec667ff1e`) are `git cat-file -t` reachable from here.

So the standing belief that *a fork whose local side is a daemon commit cannot be closed from a
seat worktree* is **too strong**. What cannot be done from here is enacting a **working-tree**
resolution (the successor `enact-the-four-path-base-wins-decision-on-the-shared-tree` is correctly
scoped to that). Closing the **ahead leg** is a commit-graph operation, and the object store is
shared, so it can.

The ahead leg is not noise. `ffa14f065..63356067f` is 9 files, +832/-575, including a 136-line new
control `..._that_composes_its_filename_is_still_a_producer.py` and `+16` to
`tools/file_scope_generated_paths.py` — the continuation of remedy step 1 of the BLOCKING finding.
It also carries `site/data/delivery.json` (553 lines) and `tick_heartbeat.json`, both **generated
against a base origin has since moved 33 commits past**.

## The prediction, before the gate runs

Door: `surgical_land --merge 63356067f --attempts 8`. `git merge-tree --write-tree` already exits 0
with no conflicted paths, so **textual conflict is not the risk** and I am not predicting it.

**P1 — the gate REFUSES the merged tree, and the cause names `site/data/`, not the code.** The two
site data files are a producer's output composed against a 33-commit-older tree; this repo's own
recurring shape is that a regenerated watched artefact reds the commit that carries it. Confidence
~60%. The code half of the leg (`file_scope_generated_paths.py` + its control) I expect to be fine.

**P2 — if it lands, `fork_state()` on the SHARED tree goes to `(N, 0)` — ahead 0, behind non-zero
and LARGER than 33**, because origin gains my merge plus whatever else lands meanwhile. That is the
success shape and it is deliberately not `contains_origin: True`: the shared tree still has to
actually fast-forward, and nothing in this turn makes it do so. **A turn that closes the ahead leg
has not closed the fork** — it has made the fork closeable without a judgement call.

**P3 — the publisher stays dark after this turn.** `behind_origin` is a fact about the checkout,
and the checkout advances when something runs a fast-forward on the shared tree, not when origin
gains a commit. I expect the next publish attempt to still report `behind_origin`. If it does not,
I was wrong about the mechanism and that is the more interesting result.

## What would refute the whole frame

If `surgical_land --merge` refuses because HEAD here is not a legal merge base, or because the door
declines a second parent it did not author, then the ahead leg genuinely cannot be closed from a
linked worktree and the successor item's scoping was right for a reason I have not understood.
Recorded so the refusal, if it comes, is a finding rather than an obstacle.

**P1 REFUTED.** The gate passed the merged tree clean (`landed MERGE f0d9442d5`). The site/data
files I expected to red it were reported by the door's own stale-copy check as *"unchanged on this
side since the merge-base"* — origin had never touched them, so there was nothing to be stale
against. **I reasoned from the AGE of the generated bytes; what governs is whether the OTHER SIDE
moved them.** Age is not staleness.

**P2 half-right, and the wrong half is a trap.** The success shape was right but the route was not:
the leg could not be pushed at all, so its content was re-landed instead. The shared tree's `ahead`
will therefore still read non-zero while its content IS on origin.

**P3 not yet gradeable** — the publisher's next attempt is the test.

**The refuting-condition clause was the useful part, and it fired.** I wrote that a refusal from
`surgical_land --merge` would mean the linked-worktree route was wrong. The merge succeeded; the
refusal came one step later from `promote_worktree_landing`, on an **ungated commit in the leg** —
a cause neither the item nor this pre-registration had considered. Both of my named hypotheses
(conflict, generated staleness) were wrong, and the thing that was actually load-bearing was not on
the list. Recorded because that is the honest shape of this measurement: the prediction's value was
in forcing the measurement, not in being right.
