# Result: the repoint instruction named a relation the tree does not record, and six of the eight rows have nothing to repoint at

Answers the prereg filed beside this today. **The prediction was 3–5 of 8 yielding an atom-own
control. It is recorded here as wrong in a way the range cannot express: BOTH numbers I could
measure were instrument artefacts, and the true answer is that the question is unanswerable.**

## What was predicted, and what the two instruments said

| | | |
|---|---|---|
| predicted | 3–5 of 8 yield an atom-own control | |
| instrument 1 | **4 of 8** | test files created by a commit whose MESSAGE names the atom id |
| instrument 2 | **8 of 8** | test files created by a commit that also touched a named SUBJECT |

Same population, same day, same tree. The two proxies disagree by a factor of two, and reading
either one's output makes the reason obvious rather than subtle:

* **Instrument 1** offered `tests/tools/test_surgical_land_rederives_on_merge.py` as
  `W2_18_the_housing_joint_the_sample_and_the_ceiling`'s own control. It arrived through commit
  `2dfc5e4fe`, *"a merge re-derives the tree's derived artefacts"*, which merely MENTIONS W2_18 —
  a `NEXT:` trailer, a claim id, map-diff prose. **A mention is not a build.** It offered
  `test_delivery_seat.py` and this very grader's own suite to `H41` for the same reason.
* **Instrument 2** yielded everything, because `simulation/population_draw.py` and
  `site/index.html` are touched by hundreds of commits and a great many of them add a test.

**There is no third, better proxy waiting to be found.** The repository records no link from an
atom to the commits that built it. "Which control did this atom's own build write" is not a
question this tree can answer, and — the part that makes it expensive — *the flattering answer is
the cheap one to reach*. Had this turn taken instrument 1 on trust it would have repointed four
level-0 rows at controls of unrelated subjects; those controls pass, so the rows would have gone
**CONTRADICTED**, turning "we cannot tell" into a false positive published as a finding.

## What the tree CAN answer, and it decides the thing the reader actually cannot see

`CONTROL_PREDATES_ROW` prints two exits — *repoint at a control this atom's own build wrote, **or**
leave the row at zero because it is right* — and nothing told the reader which. Worse, every one
of the eight reached `ungradable_causes` as `NOTHING_IN_THE_ROW`, whose repair is *"re-run it and
read the reason line"*, which is the two-exit line again. **The reader was in a closed loop whose
only terminal instruction was the unanswerable one.**

The subject's AGE is recorded, by the same oracle that already dates the controls, and it decides
the exit:

| | | |
|---|---|---|
| **6 rows** | every named subject predates the row too | the atom EXTENDS existing work; its build has written no control because at level 0 its build has not happened. **Nothing to repoint at.** |
| **2 rows** | a named subject was born AFTER the row | the build landed code and cited no control for it — the `PB4`/`PB6` shape. **The repoint is genuinely owed.** |

`D27`, `W2_18`, `W2_19`, `W2_31`, `W2_non_dd_miss_vocabulary` and `A50` are the six.
`D9_worse_than_blind_chip_is_metric_blind` (`site/harness/index.html`, born 2026-08-19 against a
row minted 2026-08-08) and `H41_the_map_ratchet_has_no_ongoing_drain`
(`tools/migrate_gain_to_store.py`, 2026-09-06 against 2026-08-10) are the two.

`W2_31` is the clearest of the six and worth naming: subject, control and row were all born on
**2026-09-08**. The row was minted alongside its own build, and a strict `born < minted` at commit
granularity calls that "predating". Nothing is wrong with the row at all.

## The drawn item's premise, corrected in the record

The item said these rows' ungradability *"is a MAP defect rather than missing work"* and that the
repair is to *"repair the map rather than the grader"*. **For this group of eight that is false,
and it is false in both directions.** It is not a map defect — six `file_scope` fields have now
been measured correct, and the one edit the item authorised (repointing) is the one edit that
would have damaged them. It is not missing work per row either. It is a third thing the partition
had no name for, and the defect was in the grader's own printed repair.

The item's count is also stale: it named **five** rows in this class and the live class holds
**eight** (`W2_non_dd_miss_vocabulary`, `W2_18`, `W2_19` are the three it does not name). A count
written into an item's prose is a prediction about an instrument.

## What landed

which is the point, and also why this cost the map ratchet zero of its 2,310 remaining bytes:

* `EXTENDS_WORK_OLDER_THAN_ITSELF`, joining `HONESTLY_UNBUILT` in `CAUSES_OWING_NO_REPAIR`. Its

  control name to move the count."*
* `BUILD_LANDED_A_SUBJECT_AND_CITED_NO_CONTROL`, which keeps the repoint instruction and names
  the younger subject to `git log`, so the reader is sent at a path rather than at a relation.

`NOTHING_IN_THE_ROW` falls **10 → 2**, and the two left (`KNIFE3`, `OPS6`) are the budget-spent
rows where its sentence — *"the refusal came from the pass and not from the row"* — is true. It
was false of the other eight.

**The owes-a-repair figure falls by six, and that is a count going down on a widened
"owes nothing" claim, which is the shape to distrust.** The guard is not that the claim is modest:
it is that it is self-clearing and falsifiable. It becomes false for a row the moment a subject
younger than that row appears in it, and the sibling cause fires instead — keyed to the property,
not to today's eight.
