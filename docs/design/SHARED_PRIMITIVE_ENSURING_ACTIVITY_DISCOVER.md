Everything in ruling §2–§4 (working-day calculator, RNG substream, size/clone ratchet, quantity
registry) is a **gate**: it fires on a diff and returns pass/fail. §5 is different in kind — it is
the standing look at the codebase *as a whole* that no gate provides, because no diff triggers it.
The four sub-mechanisms below turn that look into a repeatable activity with a named owner at each
step (register → checklist question → scheduled review → fresh-context verdict), so drift is
*discovered* the same way as every other published gap, not left to be noticed by chance.

## 5.1 Census → standing gap register

### What "the census" is

The advisor's one-off AST clone-detection pass (ruling §0: 788 modules, 70 clone-sets / 223
instances, 91 register modules, 17 working-day implementations, 1 shared utility module, VAT
touching 107 files, 2 layer back-edges) is a **snapshot**. Turning it into a standing register
means it must be **re-runnable from primary state**, not re-typed from the ruling's prose.

**Generator (BUILD half, named here so the contract is complete):** `background/shared_primitive_census.py`.
Independent read, LAW-C pattern — imports nothing from `background/supervisor.py`, exactly like
`background/primary_state_scan.py` and the GAP1 reader (`background/gap_register_scan.py`,
still-unbuilt per `docs/design/GAP_REGISTER_MINT_SOURCE_CONTRACT.md`). It walks `company/`, `sim/`,
`simulation/`, `saas/`, `background/` (tests excluded, matching the advisor's method) and emits:

- `clone_count` — structural clone-set instance count (same fingerprint method as ruling §0:
  normalise each function body to its node-type sequence, hash, group fingerprints of ≥45 nodes
  appearing in ≥2 files).
- `clone_ceiling` — the ratchet's recorded ceiling (223, per `PLANNER_MINTED_size_and_clone_ratchet_2026-07-28.md`,
  read from that mechanism once built, not re-decided here).
- `register_count` — modules under `company/` matching the register pattern (91 at census time).
- `shared_primitive_inventory` — named canonical primitives that exist vs. are still duplicated
  (working-day calculator, RNG substream primitive, `Register` base class, `log()` for the 8
  background daemons, `_clamp_term_end`, `season_for_date`, VAT constant — the ruling §3 explicit
  list — each entry: `exists: bool`, `caller_count`, `migrated_count`).
- `quantity_registry_coverage` — the §4 owned-quantity registry's coverage: which of {net margin,
  treasury, EV, bad debt, cost-to-serve, carbon} have a declared single owning module vs. none.

**Primary-state path (the published register itself):** `docs/observability/shared_primitive_census.json`
— written by the generator, read by everything downstream. This is the artefact that becomes the
gap register; the generator is the only writer, everything else (mint-source reader, phase-close
review, fresh-context evaluator) only reads it.

### Plugging into the existing gaps-as-mint-sources mechanism

This does **not** open a new mint-source mechanism. `docs/design/GAP_REGISTER_MINT_SOURCE_CONTRACT.md`
(GAP1's DISCOVER half, itself still `blocked_on director_build_open`) already names 8 registers,
each with a primary-state path and an OPEN-marking field, feeding one planned reader
(`background/gap_register_scan.py`) and one planned `gap_register` level in
`background/supervisor.py::authorized_set_enumeration()`. **The shared-primitive census becomes
register #9 in that same table**, read by that same reader, surfaced through that same level — no
second enumeration mechanism, no competing campaign (ruling §1: "adds one more register to that
list rather than opening a competing campaign").

Proposed row for the GAP1 contract table (BUILD half adds this row to
`GAP_REGISTER_MINT_SOURCE_CONTRACT.md` when the harness-BUILD front opens):

| # | Register | Primary-state path | A row is OPEN when… |
|---|----------|--------------------|-----------------------|
| 9 | **Shared-primitive census** | `docs/observability/shared_primitive_census.json` — generated by `background/shared_primitive_census.py`, re-run on the 5.3 cadence (never hand-edited) | (a) `clone_count > clone_ceiling` (drift past the ratchet's recorded ceiling — the ceiling itself is never raised by this reader, only reported against); OR (b) any `shared_primitive_inventory` entry has `exists: true` and `migrated_count < caller_count` (a canonical primitive was built but a caller still runs the old duplicate — an unfinished migration, ruling §2/§3); OR (c) any of the six named quantities in `quantity_registry_coverage` has no declared owning module (ruling §4 not yet met for that quantity); OR (d) `register_count` has grown since the last recorded census value **without** a corresponding `Register`-base-class migration note in the same window (new duplication accreting, not draining). |

### Ranking — GAP2's method, not special-cased

Ruling §1 is explicit: *"Rank it by the triage method being minted under GAP2; do not
special-case it."* `docs/design/GAP_TRIAGE_AND_RANKING.md` (GAP2, ratified per
`DIRECTOR_RULING_GAP_TRIAGE_RATIFIED_2026-07-28.md` §1) already defines the four-bucket taxonomy
(`mint` / `deliberate-and-staying` / `blocked-on-director` / `not-worth-the-complexity`) and the
ranking dimensions (fidelity impact, mission relevance, board-battery weight, blast radius, cost-
to-close). Register #9's rows are triaged through that **same** method:

- A clone-set drift row ranks on blast radius + cost-to-close (cheap, mechanical migrations rank
  high; a clone that's cheap to leave duplicated ranks `not-worth-the-complexity` with its bound
  stated — e.g. "2 call sites, 12 lines, next touch migrates it").
- A missing quantity-owner row ranks on fidelity impact + board-battery weight (the ruling names
  net margin as the worked example: three disagreeing figures ~4.2x apart is a board-battery item,
  not a tidiness item) — this is the GAP2 taxonomy doing its job, not a bespoke rule invented here.
- No row in register #9 is auto-minted; GAP2's `mint` threshold and `deliberate-and-staying` test
  apply unchanged. This design adds a **source**, not a second **method**.

### R15 — fail-CLOSED, never fail-open-empty

Matches GAP1's own invariant 2 (fail-safe toward work) applied to *this* register specifically:

- **Unreadable/missing census file** (generator never ran, JSON malformed, path absent) → the
  reader treats register #9 as **drawable/open** (not `[]`). Ambiguity forbids rest — the same
  Rule-0 direction every other register in the contract already uses, and the same direction
  `authorized_set_enumeration()`'s `_safe()` wrapper uses (a per-level read error → `True`).
- **Stale census** (generator hasn't re-run since before the last 5.3 review window) is treated the
  same as unreadable — a census that cannot have observed recent drift is not evidence of "no
  drift," it is evidence of "unmeasured," and unmeasured routes to open per the same rule.
- **R15 both-ways test (for the BUILD half to prove):** (i) delete/corrupt
  `shared_primitive_census.json` → register #9 reads OPEN (control fires; a read error must not
  silently report zero drift). (ii) restore a valid file with `clone_count == clone_ceiling` and
  full migration/coverage → register #9 reads CLOSED (clean state is provably readable as clean,
  not just "errors read open"). (iii) mutate one field past its bound (e.g. `clone_count =
  clone_ceiling + 1`) → register #9 flips back to OPEN. All three states must be distinguishable,
  not just error-vs-not.

## 5.3 Standing structural review on the retro cadence

**Cadence:** the existing retro trigger, unchanged — `.claude/skills/phase-close/SKILL.md` item 6:
*"if this phase closed a multi-day/multi-false-claim problem, or ~50 phases/2 weeks have passed
since the last retro, or a harness rule changed — run the `incident-retro` skill before closing."*
5.3 does **not** invent a new cadence or a new timer; it rides the one that already exists (ruling
§5.3: "on the existing retro cadence"), avoiding a second scheduling mechanism to maintain.

**What the review does, each time it fires:**

1. **Re-run the census.** Invoke `background/shared_primitive_census.py`, producing a fresh
   `docs/observability/shared_primitive_census.json`.
2. **Report drift**, not a verdict yet — a plain diff against the last recorded census: clone count
   delta, register count delta, any quantity that lost/gained an owning module, any primitive whose
   migration count moved. Reported as **facts**, per Anti-Goodhart below — deltas, not a score.
3. **Route through 5.4** (the fresh-context evaluator) for the verdict — 5.3 itself does not
   adjudicate whether drift is acceptable; it only produces the measured facts the evaluator reads.
4. **File the outcome** the same way every other retro produces an artifact: a dated entry under
   `docs/retrospectives/` if the drift is retro-worthy (the incident-retro skill's own bar), or —
   for routine, non-incident drift — a dated note appended to the census register itself, so the
   register carries its own history rather than requiring a second log.

**Where this differs from the ratchet (§2–§3):** the ratchet is a gate that fires on a single diff
at build time (does *this* file grow past its recorded count). 5.3 is periodic and *aggregate* — it
asks whether the whole codebase drifted over the last ~50 phases in a way no single diff would have
tripped the ratchet for (e.g. 50 phases each adding one small, individually-under-cap clone that
sum to real duplication). The two are complementary, not redundant: the ratchet catches the sharp
single instance, 5.3 catches the slow accretion the ratchet is structurally blind to.

## 5.4 Routing 5.3 through the fresh-context evaluator — the load-bearing part

**Why this is the part that matters (ruling §5.4, verbatim):** *"The same context that wrote the 91
registers is the least able to see them as a problem; a fresh context has no investment in
defending them."* 5.1–5.3 without 5.4 would just be a report the same session reads and rationalises
away — exactly the failure mode that produced 91 registers against a checklist that already asked
"does it pass" 91 times.

**Hand-off design:** 5.3's output (the census diff + any retro artifact) is handed to the
`phase-close-evaluator` agent — the same fresh-context, no-Write/no-Edit, no-memory-of-the-build
reviewer already invoked at phase close for judgement-heavy closes (`.claude/agents/phase-close-evaluator.md`
equivalent; see phase-close SKILL.md item 6c, which already records this evaluator's verdicts into
the judge-validation trust ledger). Concretely, on a 5.3 firing:

1. The orchestrator (whichever session is running the retro-triggered phase-close) launches
   `phase-close-evaluator` with: the fresh census JSON, the diff against the last recorded census,
   and pointers to the relevant registers (`docs/observability/shared_primitive_census.json`,
   `docs/design/GAP_REGISTER_MINT_SOURCE_CONTRACT.md` row 9, this design doc). **Not** the building
   session's own narrative or justification for why the drift is fine — per the ruling's own
   reasoning, that framing is exactly what a fresh context must be shielded from, mirroring
   `phase-close-evaluator`'s existing brief (it reads the diff and the checklist, not the builder's
   rationale).
2. The evaluator returns **PASS** (drift is within the ratchet + no unmigrated primitive + no
   uncovered quantity — i.e. register #9 reads CLOSED) or **NEEDS_WORK** (names the specific drifted
   item: which clone, which unmigrated caller, which quantity has no owner).
3. **On NEEDS_WORK:** the named items become GAP2-triaged rows in register #9 (5.1), entering the
   backlog exactly like any other open gap — not fixed on the spot by the evaluator (it has no
   Write/Edit tools) and not silently absorbed by the session that requested the review (§5's whole
   point is that session is the wrong judge).
4. **Record the verdict** the same way phase-close item 6c already mandates for any
   `phase-close-evaluator`/`cold-eyes-walk` verdict: `python3 -m background.judge_validation record-close
   --task-class harness_supervisor --verdict <pass|needs_work> --evaluator phase-close-evaluator
   --subject shared_primitive_census_<date>` — so a 5.3 review that later turns out to have missed
   real drift charges back to the judge's measured error rate (R15: no verdict-organ escapes
   measurement), rather than existing as an unfalsifiable rubber stamp.

**Why the existing evaluator and not a new one:** the ruling's own text calls out "the fresh-context
evaluator you already run at phase close" — this is explicitly reuse, not a new judging organ. A
second bespoke evaluator would itself be an instance of the exact incentive problem §0 describes
(building a new thing where a shared one already exists) — 5.4 would be self-defeating if it did
that.

## Anti-Goodhart (ruling §7, binding on this design)

- The census numbers (`clone_count`, `register_count`, `migrated_count`, coverage fractions) are
  **reported facts**, never a score, target, or input to any reward/fitness/selection mechanism.
  5.3's "report drift" step is explicitly a diff, not a percentage-improved headline.
- The 5.4 evaluator gives a **verdict** (PASS/NEEDS_WORK on specific named items), not a metric to
  minimise. It does not compute or report a duplication score; it names which rows are open.
  Ruling §7's warning applies directly: a clone count made a target is trivially gamed by structural
  perturbation that raises real duplication while lowering the metric — 5.4's verdict is
  item-by-item and qualitative for exactly this reason, never a single number to chase down.
- No part of 5.1–5.4 feeds the size/clone ratchet's ceiling back into a lower number by itself —
  the ceiling (223) is set once by the ruling and only ever reported against, never re-derived
  downward by this mechanism (that would be the classic Goodhart move of shrinking the yardstick).
